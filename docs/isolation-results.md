## Lost update

Lost update. Both transactions read seat 1's version, add 1 in the application,
and write it back. If both commit, one increment is silently lost: the final
version is 1, not 2. (This is the read-modify-write the optimistic strategy avoids
by putting `version = <what I read>` in the UPDATE's WHERE clause.)

## Non-repeatable read

Non-repeatable read. T1 reads seat 1's status twice in one transaction. Between
the two reads, T2 books the seat and commits. The anomaly is T1 getting two
different answers to the same question inside one transaction.

## Write skew

Write skew. Rule: at least one seat in section VIP of event 1 must stay AVAILABLE
for walk-ins. Setup leaves exactly 2 VIP seats available (1 and 2). Each
transaction counts the available VIP seats, sees 2, decides holding one is
allowed, and holds a *different* seat. Neither write touches the row the other
wrote, so no row lock conflicts, yet together they leave 0 available: the rule
is broken although each transaction checked it.
